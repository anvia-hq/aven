# The Codex agent runs on a ChatGPT login

Status: accepted

A thread can run on Codex, with the person's own ChatGPT login, beside the native agent of decision 0220. Adds to 0220 and 0222. For the Codex backend only, this supersedes the consequences in 0220 that an SDK backend calls its provider through the model gateway and that it may lack questions, restart, steering, goals and compaction.

## Choosing Codex

Codex is not a separate Agent select. Its models are the model menu's last group, "ChatGPT login · Codex" (Default, then the models of `CODEX_MODELS`), after the Claude group of decision 0244. Choosing one starts the thread on Codex, and any other model starts it on Aven's own agent. A thread keeps its backend, so inside a Codex thread the menu offers only the Codex models. A person who has no ChatGPT login is told to set one and the thread does not start.

## The login

The login belongs to one person. Settings stores the pasted access token, or a Codex `auth.json`, encrypted with `PROVIDER_ENCRYPTION_KEY`, the same key as a provider key. The API returns `{ configured, hint }`, and the hint is the last four characters of the access token. The ciphertext is never returned and never logged. There is no global token and no token shared across a workspace.

A Codex thread runs only when its owner, the person who created the thread, has a login. A teammate driving that thread uses the owner's login. The addressing gate still runs first. A thread created with `backend: "codex"` and a run of a Codex thread without a login are refused with 422 and `CODEX_LOGIN_MISSING`.

The control plane sends only the access token, never a refresh or id token from a pasted `auth.json`, and the runner receives it in memory, on `run.start`, `run.resume` and `RunSecrets`, the same way it already receives a GitHub token. It puts only the access token in `CODEX_ACCESS_TOKEN` for the Codex child, and sets `cli_auth_credentials_store` to `ephemeral`, so Codex does not write `auth.json`. `OPENAI_API_KEY` and `CODEX_API_KEY` are not passed through, and a project variable cannot stand in for the login. The session id is stored in sqlite beside the journal (`${journalPath}.codex`). The home Codex uses is `${journalPath}.codex-home`, not the person's `~/.codex`. Neither of those, nor the journal, stores the token. Access, refresh and id tokens are redacted from events and from the transcript.

Codex cannot refresh that token from disk, because the login is not on disk. When the access token expires, the person saves the login again.

`@openai/codex-sdk` and the Codex CLI it runs are Apache-2.0. Unit tests inject a query, so they do not need the CLI or a ChatGPT account. `AVEN_CODEX_FAKE=1` selects that same fake query in `e2e/codex-backend.spec.ts`.

## The wire

`AGENT_BACKENDS` is `native` and `codex`. `run.start`, `run.resume` and `RunSecrets` gain optional `codexLogin` and `codexModel`. `hello.backends` may include `codex`. All of that is optional, so `WIRE_VERSION` stays 56. A runner from before leaves the new fields unread. A control plane does not place a Codex thread on a runner that does not offer `codex`. A hello that omits `backends` still drives native only.

A Codex run does not go through the model gateway and does not use the control plane's local runner. It is placed on the thread's runtime, the same as any backend other than `native`. `model` is left off the wire for that run, so a missing provider key does not block it. Images go through attachments, `view_image`, and optional `local_image` paths.

## How the tools are hosted

Codex cannot mount an in-process MCP server. It starts the CLI, and an MCP server is a stdio process. The equivalent is a stdio MCP server named `aven` that the runner hosts. The parent listens on a short-lived unix socket inside a private (0700) folder that only this run uses. The child is this runtime (`--codex-mcp-bridge`), including the compiled `aven-runtime` binary, and it forwards each call to the in-process tool catalog: the same sandbox tools `toolsForRun` would give a native run, plus `ask_user` and `request_secret` when the run is attended.

Codex's own shell and image viewer are turned off (`features.shell_tool` and `features.view_image` are false, `sandbox_mode` is read-only, `approval_policy` is never, `web_search` is disabled). If a future Codex build still offers a patch tool, the read-only sandbox rejects the write. That is the equivalent of disallowing the tool, not an identical switch.

## What this does not do

A bot cannot run on Codex. A Codex run cannot be billed through the model gateway. The login cannot be refreshed from disk. Steering does not enter a turn that has already started. A question answered after the runner process has gone does not continue the blocked tool call; it is the next message. Goals, compaction, restart and subagents are the equivalents in the table, not the native implementations.
