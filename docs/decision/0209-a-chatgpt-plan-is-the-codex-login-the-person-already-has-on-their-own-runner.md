# A ChatGPT plan is the Codex login the person already has on their own runner

Status: proposed. The engine, the tools server, the wire and the runner's driver are built and tested against a fake `codex` program, never against real Codex; the sign-in card and its backend are built and tested in a browser with the runner's answers mocked, and not yet against a real device-code sign-in. Builds on 0006 (providers belong to the user), 0012 (the agent's tools come from the sandbox), 0021 (runs go through durable), 0177 (a thread lives on one runner), 0179 (teammates drive a thread), 0202 (the run's model gateway) and 0207 (a teammate's run is billed to the teammate). It follows the same design as 0208 for a Claude subscription; where 0208 is changed or dropped, this one follows it.

## Context

We want a person to be able to run Aven's agent on their own ChatGPT plan, through Codex, without Aven breaking OpenAI's published rules. OpenAI's rules read looser than Anthropic's, but what we found is thinner and mostly second-hand, so the design stays as strict as 0208's.

What we read (OpenAI's own help article, `help.openai.com/en/articles/20001542`, answered 403 to our fetch, so its points below come from search summaries and are to be checked at the source):

- **Codex's own sign-in** ([authentication](https://learn.chatgpt.com/docs/auth)): the person signs in with ChatGPT for subscription access or uses an API key. A ChatGPT login is cached in `~/.codex/auth.json` or the OS credential store. For a remote or headless machine the page prefers `codex login --device-auth` (beta, which the workspace has to allow). It says to "Treat ~/.codex/auth.json like a password", not to commit it, paste it into tickets or share it in chat, and it recommends API keys for CI. It does not say anything about using a subscription in another app or sharing it with teammates.
- **"Sign in with ChatGPT" for other apps** (OpenAI's help article and [coverage of it](https://www.developersdigest.tech/blog/sign-in-with-chatgpt-coding-agents-plan-usage-2026)): plan usage is a separate grant on top of sign-in. At launch it covered open-source projects, personal projects that run locally and selected private apps, and "a paid or remotely hosted app has to complete an interest form first". The app gets a `client_id` from OpenAI, runs a PKCE flow, calls the Responses API, and draws on the person's own plan allowance; the person can cap it per app in ChatGPT settings. At the limit, a call fails and is not retried on an API key. Plan usage in commercial apps is for Go, Plus and Pro plans.
- **OpenAI staff, on a fork or a separate app using ChatGPT OAuth** ([openai/codex discussion 8338](https://github.com/openai/codex/discussions/8338), December 2025 and February 2026): forks are welcome, the terms and the licence "are quite permissive", and "OSS projects like OpenCode are doing things similar". The same staff member says "I'm an engineer, not a lawyer", and does not say that "Sign in with ChatGPT" is approved for a third-party client. We do not treat this as permission.

We have not found OpenAI's terms for the Codex SDK itself, and its page does not state a licence ([Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)).

## Decision

- **A provider kind `codex`**, shown as "Codex". It has no key, no token field and no endpoint that takes one. The control plane stores nothing for it: it is a marker that says "use the Codex login on my own runner", with a status.
- **The login is the one that already exists on the runner host.** The person ran `codex login` there (or `codex login --device-auth`, which the page prefers for a machine with no browser). The runner starts Codex and Codex finds its own login. Aven never takes in, stores, forwards or reads a token, never reads or copies `~/.codex/auth.json`, and never takes a pasted one. The settings card only explains how to sign in on the runner and shows whether the runner reports a working login (signed in or not, and the method, never a credential).
- **Only on the sender's own runner, and never shared.** The same rule as 0208: a run on this kind is allowed only when the thread's runner (0177) is owned by the person sending the message (`runtimes.owner_id`). Otherwise it is unavailable, with "Use an API-key provider for this thread." A teammate's message in a multiplayer thread (0179) never uses the creator's login: it does not start a run, steer one or answer its question on it. The steering, spawn, fork and continuation rules of 0208 apply unchanged.
- **Not on the built-in runner by default.** It has no owner. The `AVEN_BUILTIN_RUNNER_OWNER` of 0208 applies to this kind too.
- **Never the server's fallback, the gateway or a proxy.** Model calls go from Codex straight to OpenAI. No run gateway token (0202), no base-URL override, no proxy. An OpenAI API key from the person's own environment is a different thing: it stays the ordinary API-key provider.
- **We do not register as an OpenAI "Sign in with ChatGPT" app.** That path means a `client_id`, an OAuth flow inside Aven and tokens that pass through it, which is what 0208 refuses for Claude. It is also the path OpenAI sends paid or hosted apps to an interest form for. If it is ever wanted, it is its own decision.
- **Signing in is Codex's own device flow, run on the runner, shown by Aven.** Amp's dialog (a screenshot of it: open ChatGPT settings, open the device-authorization page, enter a code, wait for approval) has Amp's servers hold the login. Ours has the same steps for the person, but the runner runs `codex login --device-auth` on its own host and the platform only shows what the command prints: the link and the one-time code, then "signed in" or "not". The tokens are written by Codex to its own store on the runner and never pass through Aven. The card also says that ChatGPT Business and Enterprise need an admin to allow device-code sign-in in workspace permissions (the authentication page says the same). The wire gains a request to start and cancel that sign-in and the output it relays, an optional addition if it can be.
- **The engine is the Codex SDK, run on the runner host, not in the container.** The SDK is `@openai/codex-sdk` (Apache-2.0), a thin wrapper that starts `codex exec --experimental-json` for each turn and reads its events. Codex is the agent loop here, not Aven's own (`run-driver.ts`). Its own shell and patch tools are switched off (`features.shell_tool`, `features.unified_exec`) and our sandbox tools and extras are given to it as an MCP server, so the container stays the boundary (0012) and a command the agent runs can never read the login. Codex starts with `CODEX_HOME` and an environment we build, holding no other OpenAI credential. Whether switching those tools off really leaves the model with none of its own is open (below).
- **Interactive thread runs only**, as in 0208: no goals, schedules, bots, compaction-only runs or decision model.
- **The binary is OpenAI's, as published.** It is found on the runner's `PATH` or at `AVEN_CODEX_PATH`, not patched, and not bundled in our runner binary.
- **Names.** The product says "Codex" for the provider and does not use OpenAI's marks beyond naming it.
- **API-key providers remain the recommended path**, and the only one for a team install or unattended work.
- **Wire.** The model carried by `run.start` and `run.resume` gains the kind, as an optional field if possible; otherwise `WIRE_VERSION` goes up (`docs/rules/0005-releasing.md`). It can share the field 0208 adds.

## Not settled

- OpenAI's help article was not readable by us. The eligibility and limits above are from summaries and must be checked at the source before anything ships.
- Whether running a person's Codex login on a machine that also serves their teammates' threads is acceptable to OpenAI. We avoid it by running only on the sender's own runner, but have no written answer. The interest form or a message to OpenAI is the way to ask.
- Whether Aven, as MIT open-source software that people host themselves, counts as an "open-source project" in OpenAI's sense. We read it that way; OpenAI has not said so.
- **How Aven's tools reach Codex.** What we read in the SDK's 0.167.0 package, not yet run: its options are `model`, `sandboxMode`, `workingDirectory`, `modelReasoningEffort`, `networkAccessEnabled`, `webSearchMode`, `approvalPolicy`, `additionalDirectories`, plus `config` and `configOverrides`, which become `--config key=value` for the process, and `env`, which replaces its environment. There is no way to register a tool in process. Our tools would be an MCP server (a command or a URL) named in `config` as `mcp_servers.<name>`, served by the runner, which would call into the container. The events are whole items (`agent_message`, `reasoning`, `command_execution`, `file_change`, `mcp_tool_call`, `web_search`, `todo_list`, `error`) with `item.started`, `item.updated` and `item.completed`, and `turn.completed` carries token usage. The spike has to show: that an MCP server can carry every tool we have, with its results, in the order the model asks; that `shell_tool` and `unified_exec` off leave Codex with no way to run a command (and that `apply_patch` and `view_image` can be dealt with too); and that a login in `CODEX_HOME` is what `codex exec` uses with no API key set. It needs a real ChatGPT login of the person running the spike, which we have not used. If it cannot keep 0012's boundary, this decision is dropped, not bent.
- **Steering and answering mid-run.** The SDK takes one input per `run` and starts one process per turn, so a message sent while a run is going (0098) cannot join it. On this kind it waits and starts the next turn, like a teammate's message in 0208. The agent's questions (`ask_user`, `request_secret`) end the turn and the answer starts the next one, resumed with `resumeThread`.
- **Token deltas.** Events are whole items, so the transcript fills in per item, not per token.
- **Licence.** `@openai/codex-sdk` and `@openai/codex` are Apache-2.0 (the npm registry's metadata). That is permissive, but it asks for a notice and carries a patent term MIT does not, so AGENTS.md's "raise it before adding" applies: say so in the pull request that adds it.
- Event mapping, compaction, steering and forks, models and reasoning efforts, and how the runner finds Codex on a `bun --compile` binary: as open as in 0208.

## Consequences

- Nothing is built. The next steps are the spike on tools and events, reading OpenAI's help article at the source, and a question to OpenAI.
- A team install gets nothing from this kind: each member needs their own runner with their own login.
- If 0208 is dropped or changed after Anthropic's answer, this one is reread against it, but it stands alone: OpenAI's and Anthropic's rules differ, and neither answer settles the other.

## What is built, and what it assumes

- **Wire.** `PROVIDERS` and the provider's kind enum gain `codex` (no migration: the column is text). `run.start` and `run.resume` gain an optional `codex: {modelId, reasoningEffort}` that replaces the gateway `model`, and `hello` gains an optional `codex: true` that a runner sends when it finds a `codex` binary (on its `PATH` or at `AVEN_CODEX_PATH`). `WIRE_VERSION` does not change. The control plane refuses a Codex run on a runner that has not said it can run it.
- **Control plane.** A Codex provider needs no key and no catalog. A message or an answer on it is allowed only when the thread's runner is owned by the sender (`runtimes.owner_id`), or is the built-in runner and `AVEN_BUILTIN_RUNNER_OWNER` names the sender. A question stays with the engine that asked it, and only the thread's creator answers one Codex asked. A Codex thread cannot be compacted. A run takes no gateway grant.
- **Runner.** One `codex exec` per turn through `@openai/codex-sdk`, with a built environment (only `PATH`, `HOME`, `CODEX_HOME` and a few basics, and the run's token), `sandbox read-only`, approvals never, Codex's shell (`shell_tool`, `unified_exec`) and web search off, and `developer_instructions` set to the coding agent's prompt for it. Aven's tools, including questions and the person's own MCP servers, are one MCP server on the runner's loopback, with a token per run, read by Codex from `AVEN_MCP_TOKEN`. `spawn_agent`, `define_goal` and forks are not offered, and the instructions leave out the sections about them. The Codex thread id of an Aven thread is kept in `codex-threads.json` in the runner's home. The turn is filed in the thread's history as Anvia messages, so a reload shows what the live events showed. A message sent while Codex works is refused. A runner that restarts mid-run ends the run and asks the person to send the message again.
- **Sign-in.** The runner runs `codex login --device-auth` and reads `codex login status` (exit 0 means signed in, which we saw is `Not logged in` and exit 1 with an empty `CODEX_HOME`); it parses the link and the code from the command's output, which we saw is `https://auth.openai.com/codex/device` and a code like `AOL5-C2T9O`. The control plane relays it to the runner's owner only (`POST /runtimes/:id/codex/login`, `GET /runtimes/:id/codex`) and passes on only a link under `https://auth.openai.com/`. Settings > Providers has a Codex row with the three steps of Amp's dialog: enable device code authorization in ChatGPT's settings (the link, `https://chatgpt.com/#settings/Security`, is our guess), open the device authorization page, enter the code. The provider is added once the runner reports signed in. A Codex provider is refused for a bot.

What none of this has been checked against, and has to be on a real login before it is trusted:

- that `developer_instructions` is the config key Codex reads for extra instructions (it is in the binary's strings, and in no documentation we read);
- that `shell_tool` and `unified_exec` off leave Codex no way to run a command on the host, and what `apply_patch` and `view_image` do;
- that Codex, called with the SDK's options, uses the `CODEX_HOME` login and sends no other credential;
- that the person's own `~/.codex/config.toml` cannot add MCP servers or tools that run on the host (`codex exec` has `--ignore-user-config`, which the SDK does not pass);
- how Codex counts `input_tokens` (the projector subtracts the cached ones, so they are not counted twice), and that no context window is reported;
- that Codex follows the instruction to end its turn after a question, and what it does when it does not.
