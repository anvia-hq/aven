# Persisted sandbox lifecycle, hard wall, provider draining, and spend brake

Status: accepted. Supersedes in part 0299 (expired cloud sandboxes are cleared for transparent restore rather than revoking the runtime row), 0308 (replaces in-memory idle tracking with a persisted state machine and adds a 12-hour hard wall), 0326 (every project environment row carries an `expires_at` and delete-failure backoff), and 0381 (switching or removing a provider drains its remaining resources before discarding its credentials). Adds to 0307. Decided 2026-11-20.

## Context

Cloud sandbox lifecycle state was previously split across four in-memory maps (`cloudIdle.seen`, `runtimeActivity`, `SandboxLifetime.stopsAt`, and the runner WebSocket hub) and three overloaded columns on `runtimes` (`boat_sandbox_id`, `last_seen_at`, `revoked_at`). That caused five concrete leaks and gaps:

1. **Unbounded running boxes:** An active run or a flapping runner WebSocket could extend a sandbox's provider TTL indefinitely because there was no hard wall on continuous running age, and `cloudIdle` deleted its `seen` entry on every socket disconnect, resetting the 20-minute idle floor on reconnect.
2. **Socket heartbeats extending expiry:** `runtimes.last_seen_at` was updated on every WebSocket `hello` and `close`, and fed into the 48-hour expiry query, so a reconnecting runner postponed deletion indefinitely.
3. **Orphaned snapshots without `expires_at`:** `project_environments` stored `expires_at = null` while `status = "saving"` or `"failed"`, while the expiry sweep filtered on `expires_at IS NOT NULL`, leaving stuck snapshots forever.
4. **Provider-switch credential drop:** Switching or removing the sandbox platform in Settings > Sandbox overwrote `spaces_settings` immediately, dropping the previous provider's key; existing sandboxes and snapshots could no longer be stopped or deleted, and `removeEnvironment` returned `true` when no key was present, deleting the DB row while leaking the remote snapshot.
5. **Infinite delete retries & opaque post-expiry failures:** Failed `remove()` calls stayed in the expiry query forever (risking starvation of the 100-row sweep page), and successful 48-hour expiry revoked the runtime row instead of letting the thread transparently create a fresh sandbox on its next call.

## Decision

- **Explicit persisted state machine (`cloud_sandboxes`):** Each cloud child runtime owns a `cloud_sandboxes` row with state `absent | starting | running | draining | stopping | stopped | deleting | delete_failed`, optimistic concurrency `version`, durable `running_since`, `last_activity_at`, `stopped_at`, `drain_requested_at`, `last_extended_at`, `expires_at`, `dirty`, `runtime_snapshot_name`, `delete_attempts`, `next_retry_at`, and `last_error`.
- **Provider config lifecycle (`cloud_provider_configs`):** Active credentials live in `cloud_provider_configs` (at most one `active` row via partial unique index). Switching or removing a provider marks the previous config `draining`, keeping its encrypted key solely for stopping and deleting its remaining `cloud_sandboxes` and `project_environments`. Once zero resources reference it, the reconciler wipes `api_key_encrypted` and marks it `drained`.
- **Provider capabilities and explicit credentials (`@aven/sandbox`):** `CloudProviderModule` declares `capabilities` (`stopMode: "native_resume" | "snapshot_on_stop"`, `supportsMaxLifetime`, `supportsDiskSizeQuery`, `defaultAutoStopSeconds`) and accepts optional `ProviderCredentials` on stop, extend, remove, and environment calls, so draining configs operate without mutating global settings and future providers (such as Lizard) plug in via capability flags.
- **Pure lifecycle rules in `@aven/sandbox/lifecycle`:** `decideSandboxAction`, `clampedExtendTtlSeconds`, `deleteRetryPlan`, `evaluateSpend`, and `effectiveIdleWindows` contain no database code and govern all three clocks:
  - **Activity clock:** `last_activity_at` is updated only by real agent/user work (throttled writes for terminal/file touches), never by WebSocket `hello`/`close` heartbeats.
  - **Hard wall clock (12 h default) & second lock:** `running_since` ignores activity and reconnects. Every provider `extend()` call clamps `ttlSeconds` to `min(autoStopSeconds, remainingHardWall + drainGrace)`, so the provider still stops the box if the control plane goes away.
  - **Step-boundary drain (`run.drain`):** When the hard wall, spend brake, or provider drain fires during an active run, the control plane transitions the sandbox to `draining` and sends an additive `run.drain` frame (no `WIRE_VERSION` bump). The runner steers the agent to finish its current step cleanly across native, Claude, and Codex backends; if the run does not settle within the 10-minute grace cap, the reconciler cancels it and stops the box. Archiving a thread still cancels and stops immediately.
  - **Reclaim clock (48 h stopped / 72 h project snapshot) & transparent restore:** Deleting a stopped sandbox clears `boat_sandbox_id` and transitions `cloud_sandboxes` back to `absent` without setting `runtimes.revoked_at`, so the next call lazily creates a fresh sandbox on the same thread. Failed deletes back off exponentially (`1m → 5m → 30m → 2h → 6h`) and park in `delete_failed` after 5 attempts, with an owner retry endpoint (`POST /platform/cloud/lifecycle/failed/:runtimeId/retry`).
- **Every snapshot has an `expires_at`:** `project_environments` always sets `expires_at` on insert and settle (`30m` while `saving`, `72h` when `ready`, `1h` when `failed`), sweeps null/expired/draining rows, uses provider-config credentials for removal, and backs off into `delete_failed` on persistent provider refusal. `boatModule.removeEnvironment` and `spacesModule.removeEnvironment` return `false` when credentials are unavailable instead of silently dropping the row.
- **Spend brake with soft landing:** `cloud_lifecycle` adds `maxAgeHours` (default `12`), `monthlyBudgetCents` (nullable), and `softBudgetPercent` (default `80`). `computer_usage` tracks compute sessions across sandbox state transitions rather than raw WebSocket drops, recording `estimated_cost_micros`. Reaching the soft threshold halves idle windows; reaching 100% blocks new starts in `admission.ts` and drains running sandboxes cleanly.
- **One reconciler loop:** `createCloudReconciler` replaces the three separate `cloudIdle`, `cloudExpiry`, and `environmentExpiry` timers in `server.ts`.

## Consequences

- Adding a new sandbox provider (such as Lizard) requires only its isolated folder under `sandbox/src/<name>/`, its capability declaration, and its registry entry — the state machine, drain logic, backoff, and spend brake apply automatically.
- Sandbox provider settings are stored exclusively in `cloud_provider_configs` (no dual-write or fallback to `platform_settings["spaces_settings"]`), and pre-existing cloud `runtimes` rows are lazily backfilled into `cloud_sandboxes` by the reconciler.
- Legacy already-revoked cloud runtimes remain rejected with `EXPIRED_COMPUTER`, while newly expired sandboxes reset to `absent` and transparently recreate on the next call.
