# The main bot can message other bots

Status: accepted. Builds on 0058, 0059, 0060 and 0061. The idea (`@` mentions, a bot writing to another and hearing back) is the Anvia harness's, where bots share one thread; here each bot keeps its own chat with the person, so the exchange is shaped differently.

## Context

A person with several bots wants to say to the main one, "Ask @Scout to do A, B and C", and have it hand the work over and come back with what the other bot said. Bots could not write to each other, and the composer had no way to point at a bot.

## Decision

- **The person mentions a bot with `@`** in the bot composer: a menu of their other bots, a chip in the composer, and the text `@Name` in what is sent. Only the main bot's composer has it, since no other bot can write to bots. A sent message draws `@Name` as the bot's chip, in any chat. Nothing but the text travels: the main bot reads the name against the list of bots it is given.
- **The main bot has a `message_bot` tool**, and no other bot does. It takes a bot's id and a text and returns what that bot sent back. It is a call to the control plane, `bot.ask` (wire version 27), like `bot.create`: the runner has no other bot's chat. The main bot's reply carries the person's other bots as `peers` (id, name, description), which its instructions list; `create_bot` returns the new bot's id so it can write to it in the same reply.
- **The exchange is a reply of the other bot.** The control plane queues the text in that bot's own chat, behind whatever it is answering, as `[from bot Aven] text` (`botPrompt`), has the bot answer it as it would the person, with its own model, computer and memory, and returns the messages it sent (`BotRunner.ask`, `chats.ask`). The bot's instructions say that such a message is from the person's main bot, passing on what the person asked, and that what it sends goes back to that bot.
- **The chat shows it as the Anvia harness does**: not as bubbles, but as one line that opens. A chat message may have a `peer` (`BotChatPeer`: the other bot's name and id, and `to` or `from`); messages with one that follow each other are a line in both chats: "Messaged [Scout] Scout", "Heard from [Aven] Aven", or "3 messages with …", and open, each message as `Aven → Scout text`. The asking bot's chat gets the question and the answer as it happens (`BotRunner.note`, from `chats.ask`), the asked bot's has what was asked and what it said back, and a chat read back from what a bot remembers has the same lines (`botMessagesToChat` reads `[from bot …]` prompts, the `send_message` calls after one, and a `message_bot` call with its result), with the id of a bot that was written to and only the name of one that wrote. What the app tells a bot is a `[note]`, and what the person types that starts with `[note] ` or `[from bot …] ` is kept from being read as one (`personPrompt`, a zero-width space in front), so that what is shown when it is sent and when it is read back is the same.
- **A bot just made greets its person, as in the harness.** The control plane wakes it with a note from the app, `[note] You were just created. Introduce yourself…` (`botNote`, `chats.greet`), which the chat does not show and the bot is told never to mention; what it says is in its chat, and its last words show in the sidebar. It is not waited for and a bot with no model to answer with stays quiet until spoken to. The main bot, made when a person first looks, does not.
- **It waits**: the main bot's tool call waits for the other bot's reply to end, at most five minutes (`BOT_ASK_TIMEOUT_MS`); past that the main bot is told the other is still at work and its answer will be in its chat. A bot that fails is reported to the asker as an error. A bot that sends nothing returns no replies. The runner's wait for the call is longer than the control plane's.
- **No loops**: only the main bot may write to bots, whatever the runner says (checked on the control plane in `RemoteBotReplier`), the other bot's reply is a plain one with no `peers` and no `create_bot`, a bot cannot write to itself, and only the person's own bots can be written to. A bot at its limit of waiting replies refuses more, as for the person.
- **What a bot's message is worth**: only the main bot can write, so a `[from bot NAME]` message is the main bot passing on what the person asked, and the bot treats it as the person's own request, changing itself on it too (0061). The main bot is told to say that the person asked. This puts the person's authority in the main bot's hands: a main bot that was fooled could pass on what the person never asked, which is why it is the only one with the tool and its instructions name where text may come from.
- **Messages are plain text**, up to what a person may send (`BOT_MESSAGE_MAX`, 4000 characters), and the other bot's messages come back as text, so what it saw on its computer does not.

## Consequences

- Asking is synchronous: the main bot is typing while it waits, and a slow bot makes it slow. The alternative, fire and forget with the answer arriving later as a message, needs a way to start a reply of the main bot without the person, which bots do not have.
- The other bot's chat grows with what the main bot asks it, and its memory with it; the person can read all of it.
- Bots written to are found by id, and the main bot reads `@Name` against names. Two bots with one name are told apart by their ids in its list, and the instructions say to ask the person which when they cannot be told apart.
- Other bots cannot write to each other or to the main bot; that is not built.
