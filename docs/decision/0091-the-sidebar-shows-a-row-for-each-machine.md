# The sidebar shows a row for each machine, with how loaded it is

Status: accepted. Extends 0008 (runtimes) and 0073 (install and update).

## Context

A workspace can have several runners, the machines that host every thread's and bot's sandbox. Settings > Runtimes says whether each is online and which release it is, but not whether a machine is the reason a thread is slow or will not start: its processors busy, its memory used, its disk full. Sandboxes and workspaces fill a disk quietly, and `devscalelabs-1` was at 79% when it became a runner. The person asked for a row to watch each machine, above the Settings button at the bottom of the sidebar.

## Decision

- **A runner reports how loaded its machine is.** A new runner-to-control-plane message, `host.stats` (`HostStats` in `@aven/protocol/runtime-wire`): the processors' share of time busy over the last interval, memory used and total, the disk under the runner's home (where workspaces and snapshots are kept) used and total, the number of cores and how many sandboxes are running. It is sent right after `hello` and every 15 seconds (`statsIntervalMs`). The numbers come from the operating system (`host-stats.ts`: Node's `os` and `statfs`, `/proc/meminfo` on Linux, `vm_stat` on macOS), never from a thread, so there is nothing for an agent to see or change.
- **The control plane keeps only the latest, in memory, with the connection.** `RuntimeHub.statsOf` gives it while the runner is online and `GET /runtimes` returns it as `stats` (or `null`), with `reportedAt`. It is not stored: a load history is a monitoring system's job, and a number that was true a minute ago is not worth a table. A frame with a number a machine cannot have (a percent past 100, a negative size) is dropped like any frame that does not parse.
- **No wire version change.** The control plane already ignores a frame it does not know, so a new runner talking to an older server is not refused, and an older runner simply never reports: its row says so, and that it is behind the server when it is. `WIRE_VERSION` stays 37.
- **The rows are in the shell's sidebar footer, above Settings**, so they are on every page of the app, not only in Settings, together in a card with a rule under it across the sidebar's width. There is one row for each runtime and each is one line: whether it is online, its name, and CPU, memory and disk as three small meters, each a thin upright bar that fills from the bottom beside a three-letter label over its percent. A first take had horizontal bars on the same line, where the labels and numbers ran into each other ("MEM20"), and a second put them on a line of their own under the name; the person wanted one line, with upright bars. The detail, which has no room in the row, is in a tooltip on hover (the percent and what is behind it, cores or used of total, and the sandboxes running), and a click goes to Settings > Runtimes. A meter is blue (`meter-low`) below 60%, orange (`meter`) from 60% and in the destructive colour from 90% (`meterLevel`). Machines at work come first, each group oldest first. Numbers older than a minute (`STATS_STALE_MS`: a runner reports every 15 seconds) are not shown as its load: a runner that is connected but has stopped saying reads as not reporting. A runner that is off, or does not report, is a row that says "Offline", "Waiting…" or, when it is behind the server, "Update runner", with the reason in the tooltip. The rows give way when the sidebar is collapsed to icons, and refresh with the runtime list every 10 seconds. A first version put them as cards at the top of the Settings page's menu; the person wanted them in the shell and more compact, so that is what this is.

## Consequences

- A runner needs no new setting and `aven update` brings the reporting with the new binary. Until then its row says it is waiting or behind the server.
- The first CPU number after a runner connects covers the few seconds since it started, and a reading the machine cannot give is shown as a dash with an empty bar rather than as zero.
- Disk is the disk of the runner's home, not Docker's own directory. They are the same disk on a default install; a machine that put Docker's data elsewhere will see a number that misses its images.
- Only the runtimes the person's workspace has are shown; the control plane's own built-in runner is one of them. The built-in runner is every workspace's, so its row is one machine's load seen by all of them, and its count of sandboxes running includes other workspaces'. That is a small side channel between workspaces of one installation, accepted because the load of the machine is the point of the row; an installation that must not share it should give each workspace a runner of its own.
- The runner's own report is trusted for display only: its numbers are bounded and used may not pass total, they are kept in memory and nothing is decided from them.
