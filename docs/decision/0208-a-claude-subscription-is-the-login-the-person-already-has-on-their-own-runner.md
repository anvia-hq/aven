# A Claude subscription is the login the person already has on their own runner

Status: proposed, not built. Builds on 0006 (providers belong to the user), 0012 (the agent's tools come from the sandbox), 0021 (runs go through durable), 0098 (steering), 0177 (a thread lives on one runner), 0179 (teammates drive a thread) and 0207 (a teammate's run is billed to the teammate). Replaces earlier drafts of this number that had the person paste a token into Aven.

## Context

We want a person to be able to run Aven's agent on their own Claude subscription, through the Claude Agent SDK, without Aven breaking Anthropic's published rules. The rules we read are in [legal and compliance](https://code.claude.com/docs/en/legal-and-compliance), the [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview), [authentication](https://code.claude.com/docs/en/authentication), the [Consumer Terms](https://www.anthropic.com/legal/consumer-terms) and the [plan-usage update](https://support.claude.com/articles/15036540).

The legal page says: "Developers building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication through Claude Console or a supported cloud provider. Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow." The page names Free, Pro and Max; we treat Ultra, Team and Enterprise plan logins the same. The Agent SDK page says: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK."

It also says what is allowed: nothing "prevent[s] an end user from signing in to the unmodified Claude Code binary with their own Claude subscription", and the authentication page has the person run `claude setup-token` and "set it as the `CLAUDE_CODE_OAUTH_TOKEN` environment variable wherever you want to authenticate".

How others do it, as we read it:

- Amp links a subscription in its settings and runs it "through the Claude Agent SDK on Amp's servers" ([The Dial](https://ampcode.com/docs/the-dial)). Anthropic's rules forbid a third party from storing the credential and running requests for its users unless previously approved, so we read Amp as having an agreement with Anthropic. We have not seen one, and we do not copy Amp's flow.
- opencode removed its Claude Pro/Max login in March 2026 after legal requests from Anthropic (news reports; not in its release notes). Its current "Claude Agent" provider, in the release notes of v2.2.3 and v2.2.4, has the person install Claude Code and run `claude auth login`. Claude Code makes the model calls on their machine through the Agent SDK, and opencode says it never reads or stores the credential. We follow that approach.

Plan limits: Anthropic's June 15, 2026 update says "Claude Agent SDK, `claude -p`, and third-party app usage still draw from your subscription limits", and the October 7 update says that signed in with a Claude plan, the SDK "still draw[s] from your subscription limits". The monthly API credits that Max, Ultra and Team plans now include apply only "when you run them with an API key from your linked Claude Console organization", which is an API-key provider, not this one.

## Decision

- **A provider kind `claude-agent`**, shown as "Claude Agent". It has no key, no token field and no endpoint that takes one. The control plane stores nothing for it. It is a marker that says "use the Claude login on my own runner", with a status.
- **The login is the one that already exists on the runner host.** The person ran `claude` there and signed in, or set `CLAUDE_CODE_OAUTH_TOKEN` in the runner's own environment, as Anthropic's page describes. The runner starts the Claude binary and the binary finds its own login. Aven never takes in, stores, forwards or reads a token, or reads `~/.claude/`. The settings card only explains how to sign in on the runner and shows whether the runner reports a working login. The runner checks it with `claude auth status`, run with the same environment it builds for the engine: it "exits with code 0 if logged in, 1 if not" and reports `authMethod`. Only `claude.ai` and `oauth_token` count as a subscription; `api_key` or anything else means the environment is not clean, and the run is refused. The runner reads no login file.
- **Only on the sender's own runner.** A run on this kind is allowed only when the thread's runner (0177) is owned by the person sending the message (`runtimes.owner_id`). On any other runner it is unavailable and the message says "Use an API-key provider for this thread." That covers an organization's runner another member made, the control plane's built-in runner, which has no owner, and a teammate's message in a multiplayer thread (0179), since the thread lives on the creator's runner. The creator's login never serves a teammate.
- **A teammate cannot steer or answer a run on this kind.** 0207 has a steering message keep the model its run started with, and 0202 has the run that answers a question keep the agent that asked, so either would put a teammate's words on the creator's login. While a run on this kind is going or waiting on a question, a teammate's message waits until the run ends and then starts a new run on the teammate's own provider; the agent's question is answered by the run's sender only. A teammate may still stop the run.
- **What a run hands on re-checks the rule.** An agent started by `spawn_agent`, a fork (0135) and a thread continued on another runner (0152) take this kind only if their runner is owned by the person they run for; otherwise they need another provider. The kind is never carried over by default.
- **Not on the built-in runner by default.** The control plane's built-in runner has no owner, so this kind is unavailable there. An operator who is the only person using an install can set `AVEN_BUILTIN_RUNNER_OWNER` to their user id; that runner then counts as theirs. Aven does not guess this from the number of members, which changes when someone joins.
- **Never the server's fallback.** The model a run gets when its sender has no provider (0006: `AGENT_PROVIDER` and the environment keys) is never this kind.
- **Never through the gateway or a proxy.** This kind's model calls go from the Claude binary straight to Anthropic. They do not use the control plane's model gateway or a run's gateway token (0202), and no proxy or `ANTHROPIC_BASE_URL` is set.
- **The engine runs on the runner host, not in the container.** The SDK's built-in tools are off. Our sandbox tools and extras (`ask_user`, `request_secret`, `define_goal`, `save_environment`, `show_artifact`, memory, cockpit, `spawn_agent`, `web_search`, git, MCP) are given to it as an in-process MCP server, so the container stays the boundary (0012) and a command the agent runs can never read the login. `settingSources` is empty, the working directory is a scratch folder outside the workspace, and our prompt is the system prompt.
- **The binary is Anthropic's, as published.** The runner finds it on its `PATH` or at `AVEN_CLAUDE_PATH`, or installs it from Anthropic's channel. It is not patched, none of its sign-in methods is removed or restricted, and it is not bundled in our runner binary. It is run with an environment we build, which holds no other Anthropic credential, so the subscription is what is used. A login passed by `CLAUDE_CODE_OAUTH_TOKEN` reaches only that process.
- **Interactive thread runs only.** Goals (0022), schedules, bots, compaction-only runs and the decision model do not run on this kind.
- **Names.** The product says "Claude Agent", never "Claude Code".
- **API-key providers remain the recommended path**, and the only one for a team install or for unattended work.
- **Wire.** The model carried by `run.start` and `run.resume` gains the kind, as an optional field if possible; otherwise `WIRE_VERSION` goes up and older runners are refused (`docs/rules/0005-releasing.md`). The runner reports the login's status (logged in or not, and `authMethod`, never a credential) to the control plane.

### The paste flow, not adopted

A box where the person pastes a `claude setup-token` token would make Aven take in and store the credential, which the legal page forbids a developer to do. If it is ever wanted, it is an explicit single-user mode: it works only while the install has one member who is also the runner's owner, and it switches off, and the stored token is deleted, when a second member joins. It is a fallback, it is not built, and it needs its own decision.

## Not settled by Anthropic's pages

- We read the rules above as allowing this. We have no written confirmation from Anthropic. The legal page invites questions about permitted authentication methods through its contact-sales form, and we should ask before this ships.
- The Agent SDK's "Unless previously approved" line may apply to a "Claude subscription" provider in an open-source product, whatever the design. We cannot tell from the pages.
- Consumer Terms Section 3 forbids accessing the services "through automated or non-human means, whether through a bot, script, or otherwise" except through an API key or "where we otherwise explicitly permit it". We read Anthropic's own documentation of the SDK, `claude -p` and `claude setup-token` for scripts and CI as that permission, for the person's own use.
- The Agent SDK is licensed under Anthropic's Commercial Terms, not MIT. AGENTS.md says to raise that before adding the dependency; this decision does not settle it.

## Consequences

- The control plane no longer holds a Claude token. Losing `PROVIDER_ENCRYPTION_KEY` does not affect this kind.
- An expired or revoked login is fixed on the runner, where the person runs `claude` again. The thread shows "Sign in to Claude on this runner".
- A person needs a shell on their own runner once. A member who uses an organization's runner they do not own has no way to use this kind there.
- A multiplayer thread on a creator's runner runs on the creator's login only for the creator. A teammate needs an API-key provider there.
- 0207's last bullet says a teammate's run would use the teammate's own login. Under this decision it does so only when the teammate owns the thread's runner, which for a thread on the creator's runner is never. 0207 needs a short follow-up; this decision does not edit it. The follow-up should also say that 0207's steering rule and 0202's answering rule do not apply to a teammate on this kind, as decided above.
- 0006's list of kinds gains `claude-agent`, with no key.
- Usage counts against the person's own plan, with its limits, shared with their other Claude use.

## Not checked, and open

- That the SDK, with built-in tools off and our MCP server, uses the login found by the binary, or `CLAUDE_CODE_OAUTH_TOKEN`, in a process whose environment we build.
- How the single `bun --compile` runner binary finds or fetches the Claude binary (`extractFromBunfs`, a separate install, or `AVEN_CLAUDE_PATH`).
- How a teammate's message that waits for a run on this kind is shown in the composer and the transcript.
- That `claude auth status` reports `authMethod` correctly for a login from `CLAUDE_CODE_OAUTH_TOKEN` in an environment we build (the CLI reference lists `oauth_token`; not tried).
- How SDK messages map to run events and usage, and how compaction, forks and steering (0097, 0098) map; what a runner restart does to a run in progress.
- The models and efforts the kind offers (the SDK's aliases and `effort`), and how a thread's model choice (0007) picks them.
