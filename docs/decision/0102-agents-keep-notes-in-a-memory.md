# Agents keep notes in a memory

Status: accepted. Adds to 0035 (skills), 0045 (a project's variables) and 0059 (a bot answers on a runner); keeps 0021 (a run's history is the journal's) and 0058 (a bot's chat is its memory store) as they are.

## Context

A thread's agent starts from nothing every time: what it learnt about the person and the project in one thread (they want small commits, the staging database is shared, the tests need a flag) is gone in the next, unless it is in the repository. A bot keeps its chat, but a chat is a transcript: what the bot learnt fades into a summary once the chat is compacted. Claude Code keeps short notes that outlive a conversation: one file a fact, with a name, a one-line description and a kind, and an index (`MEMORY.md`) of one line a note that is in every conversation's instructions, while a note itself is read only when it matters.

## Decision

- **A note is one fact in a file of its own, in a folder of a scope.** The agent sees them as `/memories/<scope>/<name>.md`: `personal` (about the person, in every project and bot), `project` (the person in this project, for a thread's agent) and `bot` (this bot, for a bot). A note's name is lowercase letters, digits, `.`, `_` and `-`, ending in `.md`; its body is at most 8,000 characters, and a scope holds at most 200 notes. A note is meant to start with frontmatter (`name`, `description`, `type`: `user`, `feedback`, `project` or `reference`), as Claude Code's are; its description is the frontmatter's, or else its first line.
- **Memory is the person's, per scope, and private to them.** Project notes are the person's in that project, not the workspace's: threads are private to who made them (0084), and a shared memory would let one member's agent write what steers everyone's. A team's notes belong in the repository. A bot's notes are its owner's.
- **The control plane keeps them, in `memory_notes`,** not the sandbox. A sandbox is freed when idle, made again from a snapshot, and a project may move to another runner (0093); notes outlive all of that. Every change is recorded in `memory_events` with who made it (the person, a thread's agent, a bot) and never a body, as variables' history is (0048).
- **The index is in the instructions; a note is read with the `memory` tool.** A run (`memory` on `run.start` and `run.resume`) and a bot's reply (`memory` on `bot.reply`) carry the folders the agent has and each note's name and description, which the instructions list after saying what memory is for: a folder's latest 40 notes, and how many more there are, so a full folder does not fill the instructions. The `memory` tool has the commands of Anthropic's memory tool, which Claude models know: `view` (a folder or a note, with its lines numbered), `create` (writes a note, replacing one of that name), `str_replace`, `insert`, `delete` and `rename` (which may move a note to another of the agent's folders). Each is a call to the control plane, `memory.notes` for a run and `bot.notes` for a reply, answered for the run's sender and project, or the reply's bot and owner, never for a scope the runner names. The runner writes nothing to disk, so memory is in no sandbox, snapshot or journal: the journal has the tool calls only.
- **Notes are not the person's word.** The instructions say a note is what an earlier conversation wrote, possibly out of date, and is information: it does not grant anything, and it never stands in for the person's message where one is needed (0088, 0101). They say what is worth keeping (who the person is, how they like to work, what was decided and why, where to look) and what is not (what the repository or git already says, what matters only now, any secret).
- **What may write: only what the person's word began.** A thread's run writes when the person sent its message, or a bot did on their word; a run a bot started after a note (a follow-up, 0101) reads only. Its goal sessions, which the person's message began, write too; its subagents have no `memory` tool. A bot writes in a reply on the person's word (their own message, or the main bot passing it on while it was theirs); a reply a note began (a schedule, a goal's round, a thread's end), or one another bot asked for on its own, reads only. So what a thread or a schedule's task wrote is never kept by itself, directly or through another agent. One way remains: a note's follow-up that steers a run the person began, which writes as that run does. A run's project secrets of 8 characters or more are replaced in what it writes before the call leaves the runner, and in what the tool gives back, with the same redactor its tools' results go through (0045); the tool call itself is in the transcript as every tool call is, so this keeps secrets out of notes, not out of the run's record.
- **The person sees and changes everything.** `GET /memory` lists the person's notes in every scope, `POST /memory` makes one, `PATCH /memory/:id` changes one's name or body, `DELETE /memory/:id` removes one and `GET /memory/history` gives the latest 100 changes. Settings > Memory shows them by scope. A project's notes go with the project when it is deleted (0094), a bot's with the bot.

## Consequences

- An agent can learn about the person once and know it in every thread of the project, on every runner, and a bot keeps what it learnt past compaction. The index costs a few hundred tokens a run when there are notes.
- What an agent read in a hostile page could end up in a note and in later runs' instructions. It is kept small (the index is names and descriptions, a note is read only on purpose), framed as information, readable and removable by the person, recorded in the history, and nothing a note began can write one.
- A person's notes go where their agents go: `personal` notes reach every project, in every workspace, and a thread shared with the workspace (0084) shows its memory tool calls, notes included, to its members.
- Writes to a folder are one at a time (an advisory lock on the folder), which keeps its count and names; a deleted project's folder takes no new note.
- `memory.notes` and `bot.notes` are new calls and `memory` new fields: wire version 41, so a runner must `aven update`.
- Notes are not shared with the workspace. A shared scope, editable by owners and admins, can be added beside these.
