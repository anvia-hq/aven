# Aven installs and updates with one script

Status: accepted. Replaces the nginx image of `apps/platform` and the control plane's stale Dockerfile. Partly superseded by 0219: `aven install` no longer pulls or builds a sandbox image.

## Context

Running Aven meant cloning the repository, `bun install`, `createdb`, writing about thirty variables by hand, building the multi-gigabyte sandbox image and starting `bun run dev`. Nothing was published: no release, no image, no compose file, and `apps/control-plane/Dockerfile` dated from the first commit and could not run the control plane any more. Multica installs with `curl ... | bash`, which fetches what is missing, writes a `.env` with random secrets, pulls images, starts the stack and installs a CLI; running it again upgrades.

## Decision

- **A tag `vX.Y.Z` publishes three images and a binary.** `ghcr.io/anvia-hq/aven-server` (control plane, migrations on start), `aven-web` (the built platform behind Caddy) and `aven-sandbox` (multi-arch, pulled by runners instead of built), and the `aven` binary for darwin and linux, arm64 and amd64, as GitHub Release assets (`aven-<version>-<os>-<arch>.tar.gz` and `checksums.txt`, made by `apps/cli/scripts/build-release.sh`). The repository is public, so none of it needs credentials.
- **The server is `deploy/docker-compose.yml`: Postgres, `server`, `web`.** Sandboxes are containers on a Docker daemon, and a server container has no business with its host's, so it never runs them itself. The new `AVEN_LOCAL_RUNNER=host` (next to `on` and `off`; any other value is refused) makes the built-in runner row, the one every organization sees, a separate process on the same machine: it connects with `AVEN_LOCAL_RUNNER_TOKEN` (`avrt_` and 32 or more characters, made by the installer), so a fresh install has a working runner with nothing to create in the UI, and the bots' default runner works. `deploy/docker-compose.build.yml` builds from a checkout instead of pulling. `deploy/env.example` is the settings of a self-hosted install; the root `.env.example` stays the development one.
- **`web` is Caddy**, the one published port. `/api/*` goes to the control plane with the prefix stripped (the Vite proxy's contract, which nginx did without WebSocket upgrades), everything else is the platform with a single-page fallback. `AVEN_SITE_ADDRESS` is `:80`, or a domain for which Caddy gets a certificate (`aven install --domain`, on ports 80 and 443), so HTTPS needs no further service. The server also publishes its API on loopback only (`AVEN_API_PORT`, 2837 since decision 0075): a domain site does not answer `localhost`, and the runner beside the server, `aven doctor` and `aven server status` should not depend on how the web entry point is addressed.
- **A runner is another computer.** One control plane has any number of runners, on its machine or elsewhere. A runner needs Docker, `git`, the `aven` binary and the sandbox image, and connects out to `<origin>/api` (`AVEN_URL`, the runner appends `/runtimes/connect`; the model gateway paths are relative to it). `aven` installs it as a launchd or systemd user service.
- **`install.sh` has two modes over one CLI.** By default it installs the server and a runner on the same machine; `--runner --url <origin> --token <token>` installs only a runner, and Settings > Runtimes shows that command with the token filled in. The script checks and, with the person's yes, installs what is missing (Docker, `git`), writes `.env` with random secrets and keeps an existing one, pulls, starts, waits for `/health` and opens the browser. It is fetched from `raw.githubusercontent.com/anvia-hq/aven`, with no host other than GitHub's API hard-coded, so `aven.anvia.dev` can redirect to it later.
- **`aven update` updates everything on the machine it runs on**: resolves the release, pulls the images (migrations run when the server starts), replaces its own binary, restarts the runner and pulls a new sandbox image. `AVEN_VERSION` pins a release. A runner reports its release in `hello` (an optional `build`, so no wire version change), the server returns it from `GET /runtimes` with whether it is behind the server's own `AVEN_VERSION`, and Settings > Runtimes shows "Update available"; the runtime wire version stays the hard check. Running the installer again does the same as `aven update`, and `aven install` on a machine that has a server updates it.

## Consequences

- Server state is Postgres and nothing else (the control plane only writes temporary files), so a backup is a dump of one database and `docker compose down` never loses anything but `-v`.
- A runner on a public control plane connects over `wss://`, which is why the Caddy domain mode is part of the first version and not an extra.
- GHCR may make a package private on its first push; `v0.1.0`'s were public from the start, and `docs/rules/0005-releasing.md` has the check and what to do if one is not. The `org.opencontainers.image.source` label in each Dockerfile links the packages to the repository. Pushing a tag needs no further steps (`.github/workflows/release.yml`).
- The sandbox image is pulled once per runner machine and is several gigabytes.
- Built in steps, each its own commit: the images and compose file, CI that publishes them, the `aven` CLI and runner service with a local token bootstrap, `install.sh` and the "Add runner" command, HTTPS with a domain, the runner version badge, `aven uninstall` (the services go, the database stays unless `--purge --yes`), then the GitHub App manifest flow (decision 0074), which removes the last hand-made setup (an installation cannot import a repository until a GitHub App exists).
- `v0.1.0` is the first release, published by the workflow and checked by installing from it on a clean directory (the live `install.sh`, the release's binary, the GHCR images).
- Not done: Windows (WSL2 later), and auto-update of runners.
