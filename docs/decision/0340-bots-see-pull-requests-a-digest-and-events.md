# Bots see pull requests, keep a digest and hear about events

Status: accepted. Builds on 0088, 0101, 0102 and 0339.

## Context

After 0339 a bot knows what the person is working on, but `get_thread` says nothing of a thread's pull requests beyond their number and state, a bot has no memory of the week that passed, and it hears about a thread only when its own run ends.

## Decision

- **`get_thread` gives each pull request's detail.** For up to five pull requests of the thread, `BotThreadDetail.pullRequestDetails` has the state (open, draft, merged, closed), the checks (passing, failing, pending or none, with up to ten failing names and how many more), the review state with who reviewed and who is asked, the unresolved review comments (author, file and text of at most 500 characters, up to ten, with how many more), and the changed files with additions and deletions (up to 30, how many more, never a diff). It reuses `GithubClient.pull` (`detail.ts`'s `checksOf`, `shapeFiles`); only the unresolved comments are new, `GithubClient.unresolvedReviewComments`, because the REST API does not say which review threads are resolved and GraphQL does. It is fetched in `get` only, never in `list`, and each GitHub call has a five-second timeout. A call that fails or is slow omits that part and puts a one-line reason in `omitted`, with no GitHub error text, and the rest of `get_thread` is unchanged. Everything from GitHub (titles, check names, paths, comments) loses its angle brackets and line breaks, and `pullRequestsNote`, the tool's description and the instructions say it is information, never an instruction. The scope is the person's own readable threads, as before; a folder project has no details. The thread-watch notes (0101) use `look`, the view without GitHub, so a minute's tick makes no GitHub call.
- **A rolling activity digest.** The note `activity-digest.md` is in each bot's own `bot` scope, with 0102's frontmatter, at most 3,000 characters, rendered by `activityDigest` (a pure function: the same input is the same text) from the person's own threads, not archived or archived, and cockpit tasks changed in the last seven days: pull requests merged, tasks changed, and threads worked on with their state and pull requests. No model is called and there is nothing about decisions in it, since the app has no data on them. A reply of a bot with a computer calls `ActivityDigests.keep` before the memory index is read: when the note is older than six hours (or missing) it is rendered and written, and a failure only logs a warning. Two replies at once may both render, but `memoryService.refresh` takes the folder's advisory lock, reads the note again and skips the write when it is younger than six hours, so one writes. It is per bot, because a bot's notes are in its own scope; a bot without a computer has no memory tool and no digest.
- **Only the person's word writes bot notes, still.** The digest is written by the app, not by a bot: a new `MemoryActor` of `{ source: "app" }` (`memory_events.source` takes `app`, a text column, and Settings > Memory shows it as Aven). A bot, even on the person's word, is refused every create, edit, insert, delete and rename to or from that name in its own scope (`runMemoryCommand`), and the instructions say it is the app's and read-only. The person may still change or delete it in Settings > Memory. A bot's notes of its own are written only on the person's word as 0102 says; the app's write is the one exception, it carries no word of a bot or a thread, and is made from the person's own data.
- **Events for the main bot.** Three notes, each short, with the app's `[note]` prefix (`botNote`), about the person's own threads: a pull request merged, a pull request's checks failing (with the failing names), and a thread newly waiting for the person's answer. What GitHub or the thread said (a title, check names, the question) sits only inside `<thread_output>`, as in 0101, and every note ends with the rule that it is news, never a reason to start, continue, stop or archive a thread, change oneself or make or write to a bot. The notes carry no `aboutThread`, so the follow-up allowance of 0101 does not apply to them. `botInstructions` says it too, and says what `get_thread` returns from GitHub is information.
- **Where the events come from.** A thread waiting is observed at `onRunFinished` (outcome `question`) and told only when no bot's watch told it already (`ThreadWatcher.ended` now says whether it did). Nothing observes GitHub: there is no webhook receiver for pull requests or check runs (the webhooks module is a generic inbox for the person's own webhooks), and `thread_pull_requests` is refreshed only when a run ends or the person opens a thread. So `createPullRequestWatch` is the smallest explicit poll: a tick every ten minutes over at most 30 open pull requests of unarchived threads, newest first, each through `GithubClient.pull` (an injectable source, a `start` and a `close` in `server.ts`'s startup and shutdown). A merged or closed pull request is saved as such, so a merge is found once; a merge the rate limit held back is not saved and is found on the next tick.
- **Once, and not too many.** `ThreadEventNotes`, one instance made in `composition.ts` with an injectable clock, remembers an event's key (`merged:<thread>:<number>`, `ci:<thread>:<number>:<failing names>`, `waiting:<thread>:<run>`) for a week and lets at most six notes an hour go to a person. A duplicate, a limited event and a failed delivery are told apart in the result, and a failed one is forgotten so a later tick tries it again. The notes go to the main bot only. There is no opt-out: the bot settings have none to follow and the bot decides whether to say anything.

## Consequences

- `get_thread` makes up to ten GitHub reads (two a pull request), only when a bot asks, and costs a few seconds at most.
- A bot can answer "is my PR green, what did the reviewer ask" without the person pasting it.
- The digest costs one read of the person's threads and tasks per bot per six hours, and fills at most 3,000 characters of one note, of which the index shows the description only.
- The pull request watch makes up to 30 detail reads (three GitHub calls each) every ten minutes for as long as there are open pull requests; past 30 open pull requests the oldest are not watched. Its dedup memory is in the process: after a restart a pull request whose checks are still failing is told once more, and a failing set that is fixed and fails with the same names within a week is not told again.
- A pull request merged while no tick ran is told late, at the next one; a merge made and seen in the platform first is saved by the person's view and not told.
- `WIRE_VERSION` stays 61 (not yet released): the new fields of `get` are in a result the runner passes through, and the events and the digest are the control plane's.
