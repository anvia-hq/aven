# AGENTS.md

Guidance for AI agents and contributors working in this repo.

## Overview

Bun workspace monorepo (TypeScript, ESM).

```
apps/              Applications (control-plane, platform, runtime, cli)
clients/           Native clients (macos: SwiftPM, no TypeScript)
packages/          Shared internal packages (db, agents, protocol)
docs/              Project knowledge (see docs/README.md)
deploy/            Self-hosting: compose file, env template (decision 0073)
```

## Commands

Run from the repo root.

```sh
bun install            # install deps for all workspaces
bun run dev            # start every app that defines a `dev` script
bun run typecheck      # tsc across all workspaces; must pass before committing
bun run lint           # oxlint (lint:fix to autofix)
bun run format         # oxfmt (format:check to verify only)
createdb aven          # one-time: uses your local Postgres (localhost:5432)
bun run test:e2e       # Playwright (root). Own ports 8100/5174 and database aven_e2e
bun add <pkg> --cwd apps/<name>   # add a dependency to one workspace
```

## Constraints

- **Bun only.** Use `bun`/`bunx`. Do not use npm, yarn, or pnpm, and do not commit other lockfiles.
- **Prefer Bun built-ins** (`Bun.serve`, `Bun.file`, `bun:test`, `bun:sqlite`) over third-party equivalents.
- **TypeScript strict.** No `any` without a comment explaining why. Extend the root `tsconfig.json`.
- **Internal packages** are named `@aven/<name>`, referenced as `"workspace:*"`, and exported from `src/index.ts`. Apps never import from another app. Shared code goes in `packages/`.
- **No build step** for internal packages; they ship as TS source.
- **Dependencies:** add them to the workspace that uses them, not the root (root is for tooling only). Ask before adding a heavy or new dependency.
- **Patched dependencies** live in `patches/` (`bun patch`, listed in the root `package.json`). `@anvia/durable` has one that lets an agent registration carry `toolConcurrency` (decision 0070, `docs/bugs/0005-anvia-durable-has-no-tool-concurrency.md`); it goes when Anvia has the setting upstream.
- Never commit secrets or `.env` files. Config goes in `.env` (gitignored, loaded automatically by Bun); every variable must also be listed in `.env.example` with a safe placeholder.

## Self-hosting (deploy/)

`deploy/docker-compose.yml` runs Postgres, `server` (`apps/control-plane/Dockerfile`, migrations on start, `AVEN_LOCAL_RUNNER=host`: the built-in runner is a process on the machine that connects with `AVEN_LOCAL_RUNNER_TOKEN`, decision 0073) and `web` (`apps/platform/Dockerfile`: the built platform behind Caddy, which proxies `/api/*` to the server with the prefix stripped and is the one published port). `deploy/docker-compose.build.yml` builds the images from the checkout (`docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build`); `deploy/env.example` is the install's `.env`, apart from the development `.env.example`. Both Dockerfiles build from the repository root and copy every workspace's `package.json` (a frozen lockfile needs them all). Runners are separate machines that connect out; install, update and the release pipeline are described in `docs/decision/0073-install-and-update-with-a-script.md`, and making a release, versions and what a change must keep true for `aven update` in `docs/rules/0005-releasing.md`.

## apps/cli

The `aven` command (decision 0073), one Bun binary (`bun run --cwd apps/cli build`, `dist/aven`; the release sets its version with `--define AVEN_VERSION`). `aven server install|start|stop|restart|status|logs` runs the compose file in `~/.aven/server` (`AVEN_HOME` moves `~/.aven`): the compose file and env template of `deploy/` are embedded in the binary, so it writes those of its own version, makes a new `.env` with random secrets (`env-file.ts`, `server-files.ts`) and never touches an existing one. `aven runner install --url <address> --token <token>` makes the machine a runner: it checks Docker and git, pulls the sandbox image, writes `~/.aven/runner.env` and installs a launchd agent or systemd user unit (`service-files.ts` makes the files, `service-manager.ts` drives them) that runs `aven runner run`, which is `runRunner` of `packages/runtime-client/src/run-runner.ts`, also the entry of `apps/runtime`. For a server in compose, the token is its `AVEN_LOCAL_RUNNER_TOKEN` and the runner connects as the built-in one. `aven install --domain aven.example.com` serves HTTPS (Caddy gets the certificate; `AVEN_SITE_ADDRESS`, ports 80 and 443, which `server-plan.ts` checks are free; the HTTP redirect assumes the standard ports). Who can connect is `AVEN_BIND`, the address the web port is published on: `127.0.0.1` for a new install, `0.0.0.0` with `--domain`, `--bind <ipv4>` for another; a server others can reach starts with `AVEN_REGISTRATION=closed` and `server-plan.ts` requires its `--owner-email` (decision 0079); an install made before a setting keeps what it did (`SETTINGS_BEFORE` in `env-file.ts`, empty `AVEN_BIND` is every address); `aven doctor` warns about plain HTTP open to a network and open sign-ups (`exposure.ts`); `docs/guides/cloud.md`. The server also publishes its API on `127.0.0.1:${AVEN_API_PORT:-2837}`, which the runner beside it, `aven doctor` and `aven server status` use, so they work whatever the web entry point answers to. `aven install` does the server and a runner on the machine (asking for the platform owner's email, opening the browser) and, on a machine that has a server already, brings it to the binary's release; `aven install --runner --url --token` is only a runner; `aven update` downloads the latest release's binary (`release.ts`: found by following `/releases/latest`'s redirect, checked against `checksums.txt`), swaps it in and has the new binary run `update --finish`, which updates the server (compose file, missing `.env` keys, `AVEN_VERSION`, images) and the runner (the published sandbox image, restart); `aven doctor` checks Docker, git, the server and the runner. `install.sh` at the repository root is what `curl | bash` runs: it installs git and Docker with the person's yes (Homebrew on macOS, get.docker.com on Linux), downloads and checks the binary, puts it in `/usr/local/bin` or `~/.local/bin` and runs `aven install` with the arguments it was given. `apps/cli/scripts/build-release.sh` makes the four release archives. Development and an installed Aven on one machine stay apart: set `AVEN_RUNTIME_HOME=<checkout>/.aven/runtime` in `.env` (`.aven/` is git-ignored, and lint and format skip it), so a runner started from the checkout never shares its journal, workspaces or containers with the installed runner, whose state is in `~/.aven/runtime`. Try a build against local images with `AVEN_SERVER_IMAGE=aven-server AVEN_WEB_IMAGE=aven-web aven server install --release dev`.

## packages/db

Drizzle ORM + Postgres (`postgres` driver). Source-only package, no barrel files.

- Import `db` from `@aven/db/client` and tables from `@aven/db/schema/<table>` (e.g. `@aven/db/schema/users`).
- One table per file in `src/schema/`, plural snake_case table names, `id` primary key (uuid; Better Auth tables use text ids), `created_at`/`updated_at` timestamps with time zone.
- Needs `DATABASE_URL` (root `.env`). Run scripts from the package: `bun run db:generate` (writes SQL to `drizzle/`), `db:migrate`, `db:push`, `db:studio`.
- Commit generated migrations in `drizzle/`; never edit them by hand. drizzle-kit runs on the Bun runtime (`bun --bun` in the `db:*` scripts) because it loads schema files with `require` and `@anvia/memory-drizzle` is ESM-only (`import` condition only), which fails under Node with `ERR_PACKAGE_PATH_NOT_EXPORTED`. Don't call `drizzle-kit` directly.

The native macOS client (Swift, no web view; decision 0008). ## packages/protocol

The wire protocol shared by the control plane, runtimes and every client (see decision 0008): run event types plus the pure `applyEvent` reducer (`events.ts`), and the runtime WebSocket messages (`runtime-wire.ts`; what each `WIRE_VERSION` added is in `docs/products/0005-runtime-wire-versions.md`), with the binary frame codec of a viewer's or a terminal's bytes in `viewer-frame.ts`, whose `Uint8Array.fromHex` only Bun's types declare, so the platform can import the rest. A message sent while the agent works is the events `steer_queued`, `steer` (which the reducer applies as the person's next message and a fresh reply) and `steer_rejected`, which the control plane sends, and `steer_applied`, the one a runner may send (decision 0098). A `spawn_agent` tool part carries its `subagents`, and a `subagent` event updates one of them by its index in the latest running call (decision 0057, wire version 23). `mcp.ts` has an MCP server's rules (name, header and limit) and what a bot sees of one (decision 0085). `bots.ts` has a bot's types and the events of its chat, which are not `RunEvent`s (decision 0058), with a message between bots carrying a `peer` and the prompts a bot is given for a bot's message and for the app's note (`botPrompt`, `botNote`, and `personPrompt`, which keeps what the person types from reading as either; decisions 0063 and 0065); `runtime-wire.ts` has the messages of a bot's reply, `bot.reply`, `bot.cancel`, `bot.say`, `bot.end` and the `bot.memory` call (decision 0059), the `bot.create` call with which the main bot makes another (decision 0060), `bot.update`, with which any bot changes its own name, description and instruction (decision 0061), and `bot.send`, with which a bot writes to another by its handle, a message that reaches that bot as `[from handle] text` (`botPrompt`, decision 0065; `BOT_MAX_HOPS` ends a chain of them); `bot.schedule`, with which a bot looks at, makes, changes and deletes the person's schedules, and the person's `timezone` on `bot.reply` (decision 0067); `bot.goal`, with which a bot looks at, starts and changes its goal (decision 0068, `goals.ts` has its limits and `isGoalRoundNote`); `bot.question`, with which a bot asks the person to decide, shown as `questions` on a chat message (decision 0066); `bot.thread`, with which a bot looks at the person's projects and threads and, on their word, starts, continues and archives a thread (decision 0088, `threads.ts` has the views); a bot's `avatar` is the JSON of the look the person picked, or empty (decision 0062). No runtime imports. Non-TypeScript clients follow `docs/products/0004-native-client-contract.md`. Clients (the platform) depend on this, never on `@aven/agents`.

## packages/agents

The agent engine, built on `@anvia/core` (docs index: https://docs.anvia.dev/llms.txt). Source-only, no barrel files; import from `@aven/agents/tools/<name>`.

- Tools live in `src/tools/<name>.ts` and are made with `createTool` (zod input schema). Keep them free of app and HTTP concerns; take config as options with env fallbacks and make `fetch` injectable so tests never hit the network.
- `web_search` (`tools/web-search.ts`) uses Tavily over plain `fetch`; needs `TAVILY_API_KEY`.
- The agent's tools are the sandbox's (decision 0012): `exec_command`, `read_file`, `write_file`, `list_files`, `list_ports`, `start_process`, `list_processes`, `read_process_logs`, `stop_process`, `wait_for_port` and the desktop tools, made by `createSandboxTools` in `runtime-client/src/thread-tools.ts`. `edit` (`tools/edit.ts`) and `show_image` (`tools/show-image.ts`, decision 0033: PNG/JPEG/GIF/WebP by their bytes, a copy kept by the runner) are ours, over any `{ workdir, readTextFile, writeTextFile }`. `git_fetch` (`tools/git-fetch.ts`, decision 0042) reads a branch as `origin/<branch>` through the runner's read-only token, for a person who has not connected GitHub: otherwise the agent has `gh` and `git` signed in as the sender (decision 0044). `createCodingAgent` is given it through the run driver, not built here. `spawn_agent` (`tools/spawn-agent.ts`, decision 0057) hands one to six tasks to subagents that run at the same time and returns each one's last message; `subagents.ts` has the types (`explore`, read-only by instruction, and `general`) and the tools each gets, never questions, goals, `show_image` or spawning, and `subagent-instruction.ts` their instructions. `createCodingAgent` takes them as `tools`; it does not build file or shell tools.
- What every agent shares is `agent-model.ts`: `resolveAgentModel` turns a model config (or a ready model) into the model, the provider's options, the reasoning effort and the retry policy, and `compactionFor` says when old history is summarized. The coding agent and the bot both build their own `Agent` on it; neither is built on the other, so a change to one cannot reach the other.
- A bot (decisions 0058 and 0059) is `createBotAgent` (`bot-agent.ts`): an `Agent` of its own with `send_message` (`tools/send-message.ts`: `to` is `user` or another bot's handle) and `list_bots` (`tools/list-bots.ts`), `ask_question` (`tools/ask-question.ts`, decision 0066) when its host says someone is there to answer, the goal tools (`tools/goals.ts`, decision 0068: `get_goal`, `start_goal` and `update_goal`, whose `complete` runs the goal's checks through the host first), the four schedule tools (`tools/schedules.ts`, decision 0067) and, when its host gives it a computer, the sandbox's tools (`computer`), instructions of its own (`bot-instruction.ts`, with the thread agent's `<skills>` section for the skills its host put in its computer's `/skills`, decision 0081), `create_bot` (`tools/create-bot.ts`) when its host says it may make bots, which is the person's main bot only (decision 0060), `update_self` (`tools/update-self.ts`) with which it changes its own name, description and instruction (decision 0061), the other bots listed in its instructions with their handles (decision 0065), and a `memory` store it summarizes past a size, run with `generate`, not streamed. How long a message to the person "types" is `typingDelay` (`bot-delay.ts`); the host waits it out inside the tool call, which on a runner is `BotReplies` (`packages/runtime-client/src/bot-replies.ts`). `bot-projection.ts` rebuilds a bot's chat from stored memory.
- `tools/threads.ts` is a bot's six tools for the person's threads (decision 0088), and `threads.ts` of `@aven/protocol` has what a bot sees of a thread and how a transcript is cut down for it (`threadTurns`). `commit-graph.ts` lays a page of commits out in lanes for the project page's graph (decision 0090).
- `mcp.ts` words what the agent is told of the person's MCP servers (connected or not, and that what they return is information); `tools/mcp-servers.ts` is a bot's four tools for keeping them (decision 0085). `skills.ts` reads skill folders with Anvia's loader (a broken one is left out, not fatal) and words the skill list in the agent's instructions; the agent is not given Anvia's skill tools, which run on the host, and reads a skill with `exec_command` (`cat`, since `read_file` is confined to `/workspace` and the skills are in `/skills`) and runs its scripts the same way (decision 0035).
- `attachments.ts` builds the prompt of a message with files or mentions (`sentPrompt`: the user's text, a note on the files and skills it mentions from `mentions.ts`, a note on where the files are in `/uploads`, the images) and reads it back for the transcript from the message's metadata (decisions 0034 and 0036).
- `projection.ts` turns Anvia stream events and stored messages into the `@aven/protocol` events, including a `usage` event per model call (tokens, and the context window when the model's is known: from the SDK, else from models.dev through the control plane); how a tool call and its result are shown is in `tool-projection.ts`, token and context accounting in `usage.ts`. A runner's events are checked against an allow-list in the control plane (`runtimes/wire.ts`), so a new event type must be added there too. Tests that must not hit a provider use `testing/scripted-model.ts`.
- Tool call ids are unique in a run only because `withUniqueToolCallIds` (`unique-tool-call-ids.ts`, applied in `agent-model.ts`) suffixes the `tool_<n>` ids Anvia's chat completions adapter makes for each reply; the run's events, the reducer and the thread's list all tell calls apart by id (`docs/bugs/0006-chat-stream-tool-call-ids-repeat.md`).
- Azure deployments of non-OpenAI models run on chat completions, whose stream goes through `null-free-stream.ts` (decision 0026, bug 0002).
- Compaction: history past 70% of the model's `contextWindow` is summarized by the run's own model, with no temperature, which reasoning models refuse (`compactionFor` in `agent-model.ts`, `docs/bugs/0004-anvia-summary-compactor-sends-temperature.md`); `createCodingAgent` returns it for the runner to register with durable. Without a known context window, history is kept whole. The person can compact sooner (decision 0097): `createCompactionAgent` (`compaction-agent.ts`) is the agent of a run that only does that, with a trigger of one token, no recent turn kept and a local model that answers from the request, the summary written by the person's own model.
- Nothing tells the agent a process ended; its instructions say to look with `read_process_logs`, `list_processes` and `wait_for_port`.
- Memory: the agent has no memory store; a run's history is durable's own, in the runner's journal (decision 0021). Reasoning another provider made is left out of each request by `withOwnReasoning`, and an Anthropic request gets its thinking back from the turn in progress only (`withAnthropicReasoning`; `own-reasoning.ts`, `docs/bugs/0001-anthropic-thinking-signature-across-runs.md`). The conversation the control plane keeps (written by a runner's `memory.append`, read for a thread's history) goes through `createMemoryStore(db)` in `apps/control-plane/src/memory-store.ts` (`@anvia/memory-drizzle`), whose tables live in `packages/db/src/schema/anvia-memory.ts`.
- `createCodingAgent({ provider: "openai" | "anthropic" | "azure" | "openai-compatible", tools })` (`coding-agent.ts`) assembles model + tools, including `request_secret` (`tools/request-secret.ts`, decision 0047: a second question tool whose question ids are variable names, and whose answer the control plane stores as a secret variable, the project's or the person's own, and replaces with `stored as NAME` before the run resumes: `threads/secret-answers.ts`, so the value reaches the model, the journal and the transcript nowhere) and `ask_user` (the agent asks the user: the run ends as `interaction`, the control plane keeps the continuation in `threads.pending_continuation`, and `POST /threads/:id/answer` resumes it with `run.resume`; decision 0020); `model.ts` reads `OPENAI_API_KEY` / `ANTHROPIC_API_KEY`.
- Tests are `bun:test` next to the code (`bun test packages/agents`).

## Docs

Before non-trivial work, check `docs/`:

- `docs/rules/`: conventions you must follow. These override defaults here.
- `docs/decision/`: past decisions. Do not reverse one silently; write a new one that supersedes it.

## Working style

- Keep changes small and focused; match surrounding code style.
- Run `bun run typecheck`, `bun run lint` and `bun run format` after changes.
- Record significant choices as a decision doc.
- Commit messages: short imperative subject line.
